Good questions — these are two separate things.

## Why there are still errors even though it "seems to work"

TypeScript errors are a **compile-time / editor-time** check only. Metro (React Native's bundler) uses Babel to strip types and transpile — it does not run `tsc` type-checking as part of the build. So a type mismatch like this will show up as a red squiggle in your editor (and would fail if you ever ran `tsc --noEmit` or a CI type-check step), but it won't stop the app from launching or the picker from rendering, since at runtime everything is just plain JS with no types left. That's why it "seems to function" — the errors are real, but nothing in the RN/Expo dev loop is currently enforcing them.

## What "'event' and 'event' are incompatible" means

Look at the package's own type definitions (`node_modules/@react-native-community/datetimepicker/src/index.d.ts:54`):

```ts
onValueChange?: (event: DateTimePickerChangeEvent, date: Date) => void;
```

where `DateTimePickerChangeEvent` is just:

```ts
export type DateTimePickerChangeEvent = {
  nativeEvent: { timestamp: number; utcOffset: number };
};
```

Your handler, at HistoryScreen.tsx:14, is typed:

```ts
(event: Event, selectedDate: Date) => { ... }
```

Since you never imported an `Event` type from the datetimepicker package, TypeScript resolves `Event` to the **global DOM `Event`** interface (the browser event type baked into `lib.dom.d.ts`) — a totally unrelated type with properties like `bubbles`, `cancelable`, `target`, etc.

When TS checks whether `handleDateChange` can be passed as `onValueChange`, it compares the parameter types. Because function parameters are checked contravariantly, it effectively asks "is `DateTimePickerChangeEvent` assignable to `Event`?" — and it isn't, because `DateTimePickerChangeEvent` is missing all the DOM `Event` properties. That mismatch is reported as:

> Types of parameters 'event' and 'event' are incompatible.

(the name `event` is just what both functions happen to call their first parameter — it's not significant, just how TS labels which parameter pair failed).

## There's a second, more important bug baked in

Your handler does `if(event.type === "set")` at line 16, but `DateTimePickerChangeEvent` (the real type for `onValueChange`) **has no `.type` field at all** — only `nativeEvent.{timestamp, utcOffset}`. That `.type === "set"` check is leftover logic from the deprecated `onChange` API (which uses `DateTimePickerEvent`, the one with `type: 'set' | 'neutralButtonPressed' | 'dismissed'`). It only "type-checks as fine" today because the global DOM `Event` you're accidentally using also happens to have a `.type: string` property — pure coincidence, and semantically meaningless here.

So the real fix isn't just satisfying the type checker — it's picking one consistent API:
- **Use `onChange`** (deprecated but still supported) with the package's `DateTimePickerEvent` type, keeping your `event.type === "set"` logic, and making `selectedDate` optional (`date?: Date`) to match `onChange`'s signature — or
- **Use `onValueChange`** as you have now, but drop the `.type` check entirely (it fires only on an actual selection, so no "set" check is needed) and import `DateTimePickerChangeEvent` for the parameter type.

Got it — here's the explanation without touching any files.

**The problem:** React state is local to whichever component calls `useState`. There's no mechanism for one component to reach into another component's state variable directly, and no way to "export" a live hook value across files — that's true even after your refactor moved `isAddSourceModalVisible` into `GachaScreen.tsx`. Right now `AddSourceModal` (in `GSConstants.tsx`) still references `isAddSourceModalVisible`/`setIsAddSourceModalVisible` internally, but that state no longer exists inside that component — it lives one level up, in `GachaScreen`. That's why those references are dangling.

**The solution — lift state up + pass it down as props:** This is the standard React pattern (it's exactly how a controlled `<input>` or RN's own `<Modal>` works):

1. Keep `isAddSourceModalVisible`/`setIsAddSourceModalVisible` where they already are now — in `GachaScreen.tsx`.
2. Give `AddSourceModal` two props instead of reading outer variables: a `visible: boolean` prop, and an `onClose: () => void` callback prop.
3. Inside `AddSourceModal`, use the `visible` prop everywhere it used to use `isAddSourceModalVisible` (e.g. `<Modal visible={visible} ...>`), and call `onClose()` everywhere it used to call `setIsAddSourceModalVisible(false)` — on `onRequestClose`, on the background-tap-to-dismiss, and on the BACK button.
4. In `GachaScreen.tsx`, when rendering `<AddSourceModal/>`, pass `visible={isAddSourceModalVisible}` and `onClose={() => setIsAddSourceModalVisible(false)}`.

That way `GachaScreen` still owns the single source of truth for whether the modal is open, and `AddSourceModal` never needs to see or touch that state directly — it just receives the current value as a prop and calls the callback it was given whenever it wants to ask its parent to close it. Everything else inside `AddSourceModal` (source name, dates, checkboxes, etc.) can stay as its own local `useState`, since the parent never needs to know about those.

One side note worth being aware of: `GachaScreen` currently only mounts `<AddSourceModal/>` when `isAddSourceModalVisible` is true (`isAddSourceModalVisible ? <AddSourceModal/> : null`). Once `visible` becomes a prop, you could instead render `<AddSourceModal>` unconditionally and let RN's own `<Modal visible={...}>` handle showing/hiding — the difference being that today's conditional-mount approach fully unmounts the component on every close, wiping all its internal form state (typed name, picked dates, etc.), whereas rendering it unconditionally keeps that state around between opens. Neither is "wrong" — just a UX choice.
